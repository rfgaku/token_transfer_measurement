# バリデータ投票（VoteEthDepositAction）収集：途中経過（2026-10-10 19:45 JST）

## 目的
ネイティブブリッジ deposit 117件それぞれについて、Hyperliquid L1 上の入金承認投票を取り出し、
「Arbitrum 取り込み (t1) → 各投票 → 定足数到達 → 着金 (t3)」の時刻列を再構成する。
作業フォルダは `result/validator_vote_census_20261010/` で、読み取るのは `../deposit_latency.csv` だけ。

### explorer RPC の制約
1. **毎分の制限**：公称は「重み40・毎分1,200」で、計算上は毎分30件。5分間の実測（2.2秒の固定間隔、429のあとは10秒待つ）では成功が毎分8.8件、429が21/65件だった（`rate_test.md`）。
2. **1日の上限（新たにわかったこと）**：その日の取得量が一定を超えると、HTTP 200 のまま次の応答が返る。
   `{"type":"error","message":"More than 100 archived blocks queried in one day"}`
   - 今日は約1,000ブロック取得したところ（18:29 JST）で初めてこの応答になり、19:42 の時点でも続いている。
   - メッセージは「100件」だが、実際には約1,000件取れているので数が合わない。上限の数え方（IP単位か、24時間の移動窓か、UTCの日付区切りか）は不明。
   - 「archived blocks」とあるので、古いブロックだけが対象の上限と思われる。

## データ上の注意
- `deposit_latency.csv` の `hl_block_number` は **HyperEVM のブロック番号で、L1 の高さではない**（例：exp 1 は 20306133 で、L1 のこの高さは 2023年のブロック）。
- そこで L1 の着金ブロックは「blockTime == t3（hl_ledger_time）」となる高さを補間探索して決めた。36件すべてで時刻が ms 単位まで一致した（`credit_blocks.csv`）。

## 投票取引の構造
```json
{"time": 1764226680841, "user": "0xef23…37fc",
 "action": {"type": "VoteEthDepositAction", "user": "0x322f…0321", "usd": 5000000,
            "ethId": {"b": 404580282, "t": 1, "e": "Deposit", "i": 0, "h": "0x863b…3eb5"}},
 "block": 809913323, "hash": "0x3f37…479b", "error": null}
```
- `user`（取引の外側）が投票者の署名アドレス、`time` が時刻（ms、ブロック時刻と同じ）。
- `ethId.b` は Arbitrum のブロック番号、`ethId.h` は arb_tx_hash。
- 着金後に届いた票は `error: "Deposit has already been credited."` として記録されている。

## 収集方法（`fetch_votes.py`）
- 117件を測定日ごとに分け、各日から1件ずつ順に取る並びで処理する（`order.csv`）。最大遅延の exp 77（47.3秒）は先頭30件に入れた。
- 着金ブロックから遡り、当該送金の票が16ブロック続けて現れなくなったら打ち切る。t1 より前には遡らず、着金後のブロックは取らない。
- 2.2秒の固定間隔、並列なし。429のあとは10秒待ち、1日の上限に当たったら1時間ごとに再試行する。途中で止めても再開できる。
- 1件あたり、遡りが平均19.9ブロック（17〜33）、着金ブロックの特定を含めた要求数が平均39.4。

## 途中経過（36/117件）
| 項目 | 値 |
|---|---|
| 完了 | 36件（11日分すべてを含む） |
| 投票アドレスの総数 | **4**（36件を通して同じ4つ） |
| 着金までの有効票 | **全36件で3票** |
| 拒否された票（already credited） | 30件で着金ブロック内に1票。残り6件は着金ブロック内に4票目がなかった（着金後のブロックは取っていないため未確認） |
| 遡りの打ち切り理由 | 36件すべて「16ブロック連続で票なし」 |

投票アドレス（有効票と拒否票を合わせた出現件数／そのうち拒否された件数）：
- `0x263294039413b96d25e4173a5f7599f8b3801504`：36／5
- `0xda6816df552c3f9e0fb64979fb357800d690d79b`：36／1
- `0x58e1b0e63c905d5982324fcd9108582623b8132e`：35／3
- `0xef2364db5db6f5539aa0bc111771a94ee47637fc`：31／21

**解釈の候補（未検証）**：入金承認の投票者は、21〜27ノードの合意バリデータ全体ではなく、**4つの署名者の集合**に見える。
有効3票で着金しているので、N=4、M=⌈2·4/3⌉=3 の定足数と合う。4アドレスはどれも現在の
`validatorSummaries` の signer には含まれていない。合意バリデータとは別に、ブリッジ専用の署名者集合があるのかもしれない。
議決権が等しいのか stake で重み付けされているのかは、まだ確かめていない。
これが正しければ、He & Fujihara の式(14)を当てはめる N は 4 になり、元の計画（N=21〜24 との照合）は前提が変わる。
